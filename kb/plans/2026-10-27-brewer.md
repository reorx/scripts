# brewer：按版本跨度和白名单管理 Homebrew formula 升级

## PRD

### 背景

`brew upgrade` 要么全升、要么一个个点名，`brew outdated` 一次列出一百多项，其中大半是被别的 formula 依赖才装进来的库，还有大量只差 patch 版本的小更新。真正需要我判断的，只是自己装的那些工具里跨了 Minor 或 Major 的更新；而有一批工具（gh、yt-dlp 这类）我根本不想看，有更新就该直接升。

每次手动从 `brew outdated` 里挑、再拼 `brew upgrade` 命令，既费时间，也容易漏掉或误升。

### 目标

一条 `brewer upgrade`：白名单里的工具自动升级，其余跨 Minor/Major 的更新在一个列表界面里勾选确认，patch 级更新不打扰我；结束时告诉我实际升了什么、白名单加了什么。另有 `brewer outdated` 只看不升。

### 功能与交互

#### 1. 扫描范围与版本分级

**范围**：只看 formula，不看 cask。只看我手动安装过的 formula；纯粹作为依赖被装进来的不看、不分析。手动装过、同时也被别的 formula 依赖的（如 tree、xz）照常扫描。

**版本比较**：拿本机已装的最新版本和 Homebrew 当前可升级到的版本比较，找第一个不同的位置：

| 第一个不同的位置 | 级别 | 例子 |
|---|---|---|
| 第 1 段 | Major | `13.3.0 → 14.5.0`、`v2.2.0 → v3.0.0`、`303.141.1 → 308` |
| 第 2 段 | Minor | `1.25.7 → 1.27.3`、`3.5a → 3.8`、`2026.8.19 → 2026.10.21` |
| 第 3 段及以后，或只有 Homebrew 的修订号（`_1`、`_3`）不同 | patch | `5.9 → 5.9.2`、`7.1.2-3 → 7.1.2-34`、`1.37.0 → 1.37.0_3` |

- 版本号开头的非数字前缀（`v`、`RELEASE.`）先去掉再比。
- 版本号认不出（没有任何数字）时按 Major 处理，宁可多问一次。
- 0.x 的版本同样按位置分：`0.4.6 → 0.7.0` 算 Minor。
- 被 pin 住的 formula 照常分级、在列表里标出 pinned，但不会被升级。

#### 2. `brewer outdated`：只看不升

1. 先在终端里跑 `brew update`，输出原样可见。
2. 列出过时的 formula，分 Major、Minor 两组，组内按名字排序，每行显示名字、当前版本 → 新版本；白名单里的项、pinned 的项各带一个标记。
3. 最后一行汇总：忽略了几个只差 patch 的项，`brewer upgrade` 会自动升级几个白名单项（白名单项的 patch 更新也算在内）。
4. 没有任何过时项时，只打印一行「全部是最新版本」。

#### 3. `brewer upgrade`：完整升级流程

按顺序经过下面几个阶段，每个阶段开始时在终端打印一行标题，让我知道进行到哪了。

1. **更新 Homebrew**：跑 `brew update`，输出原样可见。
2. **白名单自动升级**：白名单里有更新的 formula（不论 Major、Minor 还是 patch）逐个升级。每个开始前打印一行 `[序号/总数] 名字 当前版本 → 新版本`，然后是 brew 自己的实时输出。白名单里没有待升级项时，打印一行说明后跳过。
3. **重新扫描**：上一步可能已经连带升级了别的 formula，重新扫描一次，确认列表里只剩真正还没升的。
4. **确认界面（TUI）**：如果还有不在白名单、跨了 Minor 或 Major 的更新，进入全屏列表界面；没有就打印一行说明，跳过这一步和下一步。
5. **升级选中项**：回到终端，先打印本次选择的结果（要升级哪些、加入白名单哪些），再逐个升级选中的 formula，输出形式同第 2 步。
6. **汇总**：见下文。

#### 4. 确认界面

- 每行一个 formula：升级勾选标记、白名单标记、级别（Major / Minor，颜色区分）、名字、当前版本、新版本、一句话描述。Major 在前，Minor 在后，组内按名字排序。
- 顶部显示 Major、Minor 各有几项，已勾选几项、已标记白名单几项，随操作实时更新。底部列出可用按键。
- 打开时所有项都是未勾选状态。
- 按键：

| 按键 | 作用 |
|---|---|
| ↑ / ↓（或 k / j） | 移动光标 |
| 空格 | 切换当前项是否升级。取消勾选时，如果它带白名单标记，标记一起去掉（白名单的意思就是"总是升级"，不升级就不该进白名单） |
| d | 切换当前项的白名单标记。标记时自动勾选升级；去掉标记时升级勾选保持不变 |
| o | 在浏览器里打开当前项的主页，方便判断要不要升级 |
| 回车 | 确认，回到终端继续 |
| q / Esc | 取消：不升级任何确认界面里的项，也不改白名单（第 2 步已经完成的白名单升级不受影响），直接进入汇总 |

- 一项都没勾选就按回车，等同于"这次都不升"，照样进入汇总。
- **白名单在按下回车的那一刻就写入**，不等升级完成：升级耗时长，中途 Ctrl-C 或某项升级失败，都不会丢掉这次的白名单标记。

#### 5. 汇总

流程结束时打印，没有内容的分组不打印：

- **已升级（白名单）**：名字、旧版本 → 新版本
- **已升级（本次选择）**：同上
- **连带升级**：不在上面两组、但这次运行前后版本变了的、我手动安装过的 formula。Homebrew 升级一个 formula 时，会顺带升级依赖了它、且本身也过时的其他 formula，这里如实列出，可能包括我在确认界面里没勾选的项
- **失败**：名字和 brew 的退出码；升级命令返回成功、但运行结束后仍是过时状态的，也算失败
- **新加入白名单**：名字
- 最后一行：确认界面里没选的有几项，忽略的 patch 级更新有几项

#### 6. `brewer whitelist`：查看和编辑白名单

- `brewer whitelist`：打印白名单文件的位置和内容（每行一个 formula 名）。
- `brewer whitelist add <名字>...`：加入白名单，已存在的不重复加；名字不是本机手动安装的 formula 时给出提示，但仍然加入。
- `brewer whitelist rm <名字>...`：从白名单移除，不存在的给出提示。
- 白名单文件也可以直接手工编辑：一行一个 formula 名，`#` 开头的行和空行忽略。名字写短名（`stripe`）或带 tap 的全名（`stripe/stripe-cli/stripe`）都能匹配。

#### 7. 选项

- `--no-update`（`outdated`、`upgrade` 都有）：跳过 `brew update`，直接用本地已有的数据，反复运行时更快。
- `--dry-run`（`upgrade`）：完整走一遍流程，包括确认界面，但不执行任何升级，也不改白名单；原本要执行升级的地方打印将要执行的命令。

#### 8. 出错和边界情况

- **找不到 brew**：打印提示后退出，退出码非 0。
- **`brew update` 失败**：打印警告，继续用本地数据往下走（可能不是最新信息）。
- **某个 formula 升级失败**：继续升级后面的，汇总里列入「失败」，整个命令以非 0 退出码结束。
- **升级过程中按 Ctrl-C**：中断当前这一项，不再升级剩下的，仍然打印汇总（被中断的那项算失败），以 130 退出。
- **不在交互式终端里运行**（如被脚本或定时任务调用）：照常做白名单自动升级；需要确认的项不进确认界面，只在终端列出、不升级。
- **白名单文件不存在**：视为空白名单；第一次需要写入时自动创建。

### 不做的事

- cask 的升级和检查。
- 降级、回滚、卸载、`brew cleanup` 之外的清理（brew 升级后自己会做的清理照常发生）。
- 阻止 Homebrew 的连带升级：只如实汇报，不干预。
- 依赖型 formula 的单独展示或分析。
- 确认界面里的全选、搜索、排序切换。
- 定时自动运行。

### 验收标准

- [ ] `brewer outdated` 先跑 `brew update`，再按 Major / Minor 分组列出过时项；只差 patch 的不出现在列表里，数量出现在最后一行
- [ ] 纯依赖装进来的 formula 不出现在任何列表里；手动装过、同时被依赖的出现
- [ ] 版本分级符合「版本比较」表里的每一个例子
- [ ] 白名单里的 formula 有更新（含 patch）时，`brewer upgrade` 不经确认自动逐个升级，能看到每一个的实时输出
- [ ] 白名单升级完成后，仍有需要确认的项时进入确认界面；没有时不进入
- [ ] 确认界面里空格切换升级、d 切换白名单并自动勾选升级、o 打开主页、回车确认、q 取消，都按「确认界面」一节的描述工作
- [ ] 回车后回到终端，逐个升级选中项，输出实时可见
- [ ] 回车时白名单立即写入；之后 Ctrl-C 中断，白名单里仍有本次标记的项
- [ ] 汇总分别列出白名单升级、本次选择升级、连带升级、失败和新加入白名单的项
- [ ] 某一项升级失败不影响后面的项，命令最终以非 0 退出码结束
- [ ] `--dry-run` 不执行任何升级、不改白名单；`--no-update` 不跑 `brew update`
- [ ] `brewer whitelist`、`add`、`rm` 能查看和增删白名单，手工编辑的注释在增删后保留

## Tech Design

### 现状

仓库里没有 Homebrew 相关脚本。可参照的是 `mole-review.py`：textual TUI、`~/.config/<工具>/whitelist` 纯文本白名单（带头注释，追加写入，删除只去掉匹配行）、测试用 PATH 里的假可执行文件冒充外部命令（`test_mole_review.py` 的 `TestRescan`），以及把 `App.run` 换成桩来测主流程。

本机 brew 7.0.11 的数据形状（`tmp/brewer/` 里存了一份样本）：

- `brew outdated --json=v2 --formula`：`formulae[]` 里每项有 `name`（tap formula 是全名，如 `stripe/stripe-cli/stripe`）、`installed_versions`（按版本升序，取最后一个即已装最新版）、`current_version`、`pinned`。约 0.4s。
- `brew info --json=v2 --installed`：`formulae[]` 里有 `name`（短名）、`full_name`（核心 formula 与 `name` 相同）、`desc`、`homepage`、`installed[].installed_on_request`。约 1.1s。手动安装 = 任一 keg 的 `installed_on_request` 为真。
- `brew upgrade` 默认会对过时的 dependents 也跑升级（`HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK` 关闭），这就是 PRD 里「连带升级」的来源。

### 方案

单文件 `brewer.py`（PEP 723，依赖只有 `textual>=8.0`），`./link-script brewer.py` 链接成 `brewer`。数据只来自上面两个 JSON 命令；每次扫描都是「info 取手动安装集合 + 描述/主页，outdated 取版本」合并后的 `Formula` 列表。

关键决策：

- **按 formula 逐个 `brew upgrade --formula <name>`**，不一次传多个：每项的输出、退出码、失败都能单独归属，汇总才准确。代价是每次多约 1s 的 brew 启动开销，可以接受。`--formula` 防止和同名 cask（如 docker）混淆。
- **升级子进程设 `HOMEBREW_NO_AUTO_UPDATE=1`**：update 已由我们自己做过（或被 `--no-update` 显式跳过），不让每次 upgrade 再触发。
- **连带升级靠前后两次扫描求差**：运行开始扫描一次（before），结束再扫描一次（after）。尝试过且退出码 0、after 里不再过时的算成功；before 里有、after 里没有、又没尝试过的算连带。不解析 brew 的文本输出——那不稳定。
- **分级只看版本号 token**：去掉结尾 `_\d+`（brew revision），拆成数字段和字母段，丢掉第一个数字段之前的字母段，找第一个不同的下标：0 → major，1 → minor，≥2 或全同 → patch；任一方没有数字段 → major。不做大小比较，不需要处理数字和字母混比。
- **白名单名称匹配**：短名或全名任一相等即视为同一个 formula（`same_formula`）。写入时用 brew outdated 报出的名字（tap formula 写全名）。
- **TUI 用 textual 全屏模式**（不用 inline）：七十多行的列表需要整屏；退出后终端回到原来的滚动内容，后续输出接着打印。
- **终端输出用 print + 简单 ANSI 着色**（stdout 是 tty 且没设 `NO_COLOR` 时），不用 rich Console：输出简单，测试里直接比对文本。
- **错误只在命令层处理**：`brew_json` 失败直接抛 `CalledProcessError`，`main` 统一转成错误信息；Ctrl-C 在 `cmd_upgrade` 里统一捕获。

被否决的：`brew leaves` 作为范围（用户选了「手动安装过的」）；`HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK=1`（会让跳过的 formula 链接损坏，用户选了如实汇报）；TOML 配置（stdlib 不能写 TOML，而且重写会丢注释）。

### 数据变动

新增 `~/.config/brewer/whitelist`：纯文本，一行一个 formula 名，`#` 注释和空行忽略。不存在时视为空，首次写入时创建，开头带两行说明注释。`add` 只在末尾追加，`rm` 只删掉匹配的行，其余内容原样保留。

### 逻辑变动

新文件 `brewer.py`，分节：

- **versions**：`version_tokens(v)`、`version_level(old, new) -> 'major'|'minor'|'patch'`。
- **brew**：`brew_json(*args)`（capture，`check=True`）、`brew_run(*args)`（继承 stdio，返回退出码，带 `HOMEBREW_NO_AUTO_UPDATE=1`）、`scan() -> list[Formula]`、纯函数 `parse_scan(info, outdated)` 供测试。
- `@dataclass Formula`：`name, installed, latest, level, pinned, desc, homepage`。
- **whitelist**：`short_name`、`same_formula`、`load_whitelist`、`in_whitelist`、`add_to_whitelist(path, names) -> 新增的`、`remove_from_whitelist(path, names) -> 删掉的`。
- **plan**：`@dataclass Plan(auto, review, ignored, pinned)`，`make_plan(formulae, whitelist)`：pinned 先分出去；白名单内 → auto；其余 patch → ignored；major/minor → review，按 (major 在前, 名字) 排序。
- **tui**：`@dataclass Choice(upgrade, whitelist)`；`ReviewApp(App[Choice | None])`，状态是两个名字集合，按键语义按 PRD 表格实现；`enter` 用 priority binding（DataTable 自己绑了 enter）。
- **upgrade**：`@dataclass Attempt(formula, phase, code=None)`，`upgrade_each(formulae, phase, attempts, dry_run)` 先登记 attempt 再跑，Ctrl-C 时最后一个 attempt 的 code 为 None 即被中断的那项；`summarize(before, after, attempts, whitelisted, plan, ...)` 生成汇总行。
- **commands**：`cmd_outdated`、`cmd_upgrade`、`cmd_whitelist`；`main(argv=None) -> int`。子命令共享 `--whitelist PATH`（默认 `~/.config/brewer/whitelist`，测试用）；`outdated`/`upgrade` 有 `--no-update`，`upgrade` 有 `--dry-run`。`is_interactive()` 判断 stdin/stdout 都是 tty，非交互时跳过 TUI。

`--dry-run` 下 `brew_upgrade` 只打印 `would run: brew upgrade --formula <name>`、返回 0，结束时不做 after 扫描，汇总分组标题改为 "Would upgrade"，不出现连带和失败组。

`AGENTS.md` 加一小节：脚本作用、白名单位置、测试命令。

### 测试与验证

`test_brewer.py`（`uv run test_brewer.py`），假 brew 是写进临时 bin 目录的 Python 脚本，状态放在临时目录的 `info.json`/`outdated.json`，调用记录追加到 `calls.log`；`upgrade` 时从 `outdated.json` 删掉该项（以及 `effects.json` 里声明的连带项），并把当时的白名单内容记进日志；`FAKE_FAIL` 指定失败项，`FAKE_INTERRUPT` 指定的项向父进程发 SIGINT 模拟 Ctrl-C，`FAKE_UPDATE_EXIT` 控制 update 退出码。

|---|---|

| 纯依赖不出现、手动+被依赖的出现 | `TestScan` |
| 分级符合表格例子 | `TestVersionLevel`（逐例） |
| 白名单自动逐个升级 | `TestUpgradeCommand`：calls.log 里 update 后依次 upgrade 白名单项，TUI 之前 |

| 回车后逐个升级选中项 | calls.log |
| 回车即写白名单、Ctrl-C 后仍在 | 假 brew 记录 upgrade 时的白名单内容；`FAKE_INTERRUPT` 用例检查文件和退出码 130 |
| 汇总分组 | 断言输出包含各组及条目，含连带升级（effects.json） |

### 风险与待定

- `installed_versions` 升序是从样本观察到的（`0.3.75` 排在 `0.3.110` 前，说明是按版本而非字符串排），brew 文档没写保证。若将来顺序变了，分级会拿错基准版本。
- 日期型版本（`2026.9.1 → 2026.10.4`）按规则落在 Minor，每月都会进确认界面；这类工具适合直接加白名单。
- 真实升级只能由用户自己跑来验收，开发中不动本机已装的 formula。
